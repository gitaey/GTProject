# fullstack-pipeline

planner → (backend-dev ∥ frontend-dev / map-dev) → qa 순으로 서브에이전트를 조율한다.
메인 세션(너)이 리더다: 에이전트를 호출하고, 사용자 승인을 받고, 결과 파일을 모으고, 브라우저로 확인한다.

**실행 방식:** 서브에이전트. `Agent` 도구에 `subagent_type`으로 에이전트 이름을, `model: "opus"`를 항상 넘긴다.
병렬은 한 메시지에 여러 `Agent` 호출 + `run_in_background: true`. 이미 실행한 에이전트에게 수정을 시킬 때는
새로 띄우지 말고 `SendMessage`로 이어서 지시한다(맥락이 남아 있어 빠르고 정확하다).
**데이터 전달:** `_workspace/<slug>/` 파일 + 에이전트 반환값. `<slug>`는 영문 kebab-case 기능 이름.

## Phase 0 — 상황 판단

- `_workspace/<slug>/`가 있고 사용자가 부분 재실행을 원함("QA만 다시") → 해당 Phase만 실행.
- 있는데 새 요청 → 기존 폴더를 `_workspace/<slug>_prev_<YYYYMMDD>/`로 옮기고 처음부터.
- 없으면 처음부터.

## Phase 1 — 담당 정하기

| 건드리는 영역 | 담당 |
|---|---|
| `backend/`, `bot/` (지도 도메인 제외) | backend-dev |
| 프론트 화면 (지도 제외) | frontend-dev |
| 지도 모듈·지도 페이지·지도 백엔드 도메인(map, mymap, geoserver, geotiff, wind) | map-dev |

지도가 조금이라도 끼면 그 부분은 반드시 map-dev에게 준다. 이식성 계약을 아는 에이전트가 map-dev뿐이다.

## Phase 2 — 설계와 승인

1. `planner`를 **포그라운드로** 호출한다(다음 단계가 이 결과에 달려 있음). 프롬프트에 요청 원문, slug,
   Phase 1의 담당 배정, 관련 파일 위치를 준다.
2. planner가 질문을 돌려주면 사용자에게 묻고, 답을 `SendMessage`로 planner에게 전달해 설계를 마무리시킨다.
3. 사용자에게 설계 요약(요구사항, API 계약, 화면/목업 링크, 작업 순서, 담당)을 보여주고 **승인을 받는다.**
   이 파이프라인에서 사용자에게 멈춰 묻는 곳은 여기 한 곳이다. 수정 요청이 오면 planner에게 반영시키고 다시 보여준다.

## Phase 3 — 구현 (병렬)

승인되면 담당 에이전트를 **한 메시지에서 동시에** 백그라운드로 호출한다. API 계약이 설계문서에 확정돼 있으므로
백엔드와 프론트가 서로를 기다리지 않는다. 각 프롬프트에 설계문서 경로, slug, 산출물 파일명, 맡은 체크리스트 항목을 준다.

기다리는 동안 사용자에게 무엇이 돌고 있는지 짧게 알린다. 결과를 예측해서 말하지 않는다.

## Phase 4 — QA (점진적)

- 구현 에이전트 하나가 끝날 때마다 `qa`를 백그라운드로 호출해 **그 모듈을** 설계 계약과 대조시킨다.
- 모든 구현이 끝나면 `qa`를 한 번 더 호출해 백엔드↔프론트 **경계면 교차 비교**를 시킨다.
- qa가 실패를 보고하면 수정 요청을 해당 구현 에이전트에게 `SendMessage`로 보내고, 끝나면 qa를 다시 돌린다.
  **최대 2회.** 그래도 남으면 남은 문제를 목록으로 들고 Phase 6으로 간다.

## Phase 5 — 브라우저 확인 (메인이 직접)

화면이 바뀌었으면 에이전트들이 적어준 시나리오대로 개발 서버를 띄워 직접 조작해본다(`preview_start` →
`read_page`/`computer`/`read_console_messages`). 로그인이 필요해 확인하지 못한 부분은 못 했다고 보고한다.

## Phase 6 — 마무리

- 사용자에게 보고: 만든 것, 검증한 것(명령과 결과), 확인하지 못한 것, 남은 문제, 필요한 SQL/설정.
- planner에게 `SendMessage`로 설계문서 상단에 `구현 완료` 표시를 시킨다.
- **commit/push하지 않는다.** 사용자가 요청하면 그때 한다. push는 곧 배포다(`deploy.md`).
- "진행 방식이나 결과에서 바꾸고 싶은 점이 있나요?"라고 묻는다. 에이전트/스킬을 고치게 되면
  CLAUDE.md 하네스 변경 이력에 기록한다.

## 에러 처리

| 상황 | 대응 |
|---|---|
| 에이전트가 완료 조건(tsc/compile/audit) 실패로 반환 | `SendMessage`로 에러를 주고 1회 재시도, 또 실패하면 보고에 포함하고 진행 |
| 구현 에이전트가 "다른 담당 영역"이라고 반환 | 그 부분만 떼어 올바른 담당에게 준다 |
| 설계와 구현이 충돌 | 임의로 정하지 않는다. 계약이 틀렸으면 planner가 설계를 고치고, 구현이 틀렸으면 구현 에이전트가 고친다. 애매하면 사용자에게 묻는다 |
| 에이전트 결과 없이 종료 | 1회 재호출, 또 실패하면 그 단계 없이 진행하고 보고서에 누락을 명시 |
| `Agent type '<이름>' not found` | 에이전트 목록은 세션 시작 때 읽힌다. 같은 세션에서 새로 만든 에이전트면 `subagent_type: "general-purpose"`로 호출하고 프롬프트 첫 줄에 "`.claude/agents/<이름>.md`를 읽고 그 역할·원칙·산출물 규칙을 그대로 따른다"를 넣는다 |

## 테스트 시나리오

- **정상:** "관리자에 공지사항 기능 추가해줘" → backend-dev + frontend-dev 배정 → planner 설계·목업 → 승인 →
  두 에이전트 동시 구현 → 각각 끝날 때 qa → 경계면 qa 통과 → 메인이 `/admin/notice` 브라우저 확인 → 보고.
- **에러:** qa가 "백엔드는 `createdAt`, 프론트는 `createDate`" 보고 → 계약이 `createdAt`이므로 frontend-dev에게
  `SendMessage`로 수정 요청 → qa 재실행 통과 → 보고서에 "경계면 불일치 1건 수정" 기록.
